<objective>
Extract the pg.Pool out of src/lib/prisma.ts into a neutral module (src/lib/db-pool.ts) carrying the audit §25.2 pinned options, and re-wrap Prisma on top of it — one pool per process, owned by neither ORM, ready for the Drizzle client (plan 03-04) and the Phase 4 worker's own pool.

Purpose: DAT-09 (connection budget enforced in code: web max 10, timeouts pinned) and the D-06 shape Prisma + Drizzle will share for the rest of the transition. This plan is deliberately Prisma-only — it proves the extraction breaks nothing before Drizzle attaches to the same pool.

Output: src/lib/db-pool.ts (new), src/lib/prisma.ts (amended to consume it), tests/integration/db-pool.test.ts proving the pinned options and the shared instance.

## Phase Goal (user story)

**As a** SpiderNode user, **I want** the platform beneath my uptime monitors modernized — rate limiting that survives restarts and a schema owned by rehearsed, versioned migrations — **so that** my checks, alerts, and history keep flowing through every deploy without data loss or lockouts.

This plan builds the pool the whole modernization shares: after it, Postgres connections come from one budgeted, timeout-guarded pool that both ORMs (and later the worker) hang off — with Prisma behaving exactly as before.
</objective>
