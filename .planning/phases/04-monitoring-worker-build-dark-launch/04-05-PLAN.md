<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Redis staging buffer → Postgres counters | Aggregated deltas cross from a cache into authoritative rows; guards must make re-application impossible |
| concurrent flushers → one staging key | Two workers may race to flush the same monitor |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-17 | Tampering | double-applied counters on crash-after-COMMIT redelivery | critical | mitigate | RENAMENX ownership + write_guards ON CONFLICT DO NOTHING + same-transaction application (DAT-03); case-(5) test is the proof |
| T-04-18 | Tampering | Tier 2 overwriting monitor status and racing Tier 1 transitions | high | mitigate | The UPDATE never references status (structural + sentinel test); additive-only math |
| T-04-19 | Denial of Service | unbounded staging growth on Redis (512 MB noeviction) | medium | mitigate | ≤60 s flush cadence, snapshot key deleted post-commit, maintenance dry-run (04-07) reports staging/queue key sizes |
| T-04-20 | Tampering | lost staged results if Redis restarts mid-window | medium | accept | By-design ceiling: at-most ~60 s of routine-UP EVIDENCE may drop on a Redis crash; counters/monitors are never corrupted (Postgres authority) — consistent with the design's Redis-is-staging-only contract; recorded in SUMMARY |
</threat_model>
