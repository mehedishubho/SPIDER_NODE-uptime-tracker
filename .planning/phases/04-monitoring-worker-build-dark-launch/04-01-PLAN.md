<objective>
Stand up the dedicated worker process as a real, bootable, health-reporting artifact: dependencies installed, one `pnpm build` producing web + worker bundles (D-06), a boot entry that loads dotenv first (D-12), a BullMQ-shaped Redis connection factory, pino structured logging (D-14), the `:9090` health surface (WRK-08, D-13), graceful shutdown handlers (WRK-07), the worker's budgeted pg pool (max 20), the worker/Next boundary verify gate (D-08), the PM2 worker app definition (D-20), and `.env.example` additions.

Phase Goal (derived from ROADMAP): as the operator, I want all monitoring execution running on a dedicated worker process on durable, idempotent, resilient BullMQ machinery, dark-launched with its scheduler paused, so that the existing cron keeps serving every user while the new machinery is proven safe. This plan delivers the first slice: the operator can build, boot, and health-check the worker process.

Purpose: Every later Phase 4 plan (queues, claim, persistence, relay, resilience, dark launch) boots from these modules and gates; DEP-01's same-SHA claim becomes runtime-verifiable here (D-10).
Output: A bootable `dist/worker.js` with health endpoints, boundary/build gates inside `pnpm verify`, and the PM2 worker stanza.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry → node_modules | New third-party code enters the repo (bullmq, pino, undici, tsup, tsx) |
| localhost HTTP → worker health endpoints | Any local process can reach :9090 |
| worker → Redis/Postgres | Worker authenticates with existing REDIS_URL/DATABASE_URL credentials |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-SC | Tampering | npm installs (bullmq/tsx/undici flagged SUS by recency heuristic) | high | mitigate | Blocking human-verify checkpoint (Task 1) against npmjs.com registry pages; zero [SLOP] packages per audit |
| T-04-01 | Information Disclosure | health/metrics endpoints | medium | mitigate | Bind 127.0.0.1 only; payloads carry provenance/status only — no connection strings, tokens, or env values |
| T-04-02 | Denial of Service | unauthenticated local HTTP surface | low | accept | Loopback bind on a dedicated port; stand-in topology is single-operator; PM2/VPS exposure reviewed at first VPS deploy (forward-tracked) |
| T-04-03 | Information Disclosure | pino stdout logs | medium | mitigate | Logger bindings restricted to ids/timings/levels; no URL/token interpolation in worker modules (secrets rule) |
</threat_model>
