## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| outbox rows → Telegram API | Alert delivery crosses to an external service; user trust depends on exactly-once-per-incident semantics |
| maintenance real-run → destructive deletes | The only batched delete surface in the worker; bounded and lane-gated |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-25 | Tampering (user-trust) | duplicate alerts on relay retries/redrives | high | mitigate | Incident-keyed SET NX EX after confirmed send + skip-but-mark-sent on existing key + ≤3 attempt cap + FAILED retain (DAT-06/D-44/D-47); parity tests pin content |
| T-04-26 | Denial of Service | alert storms during incident flapping amplified by retries | medium | mitigate | Dedup keys make re-sends impossible within TTL; terminal FAILED stops retry storms; outbox-age alerting rides in Phase 5 (OBS-03) |
| T-04-27 | Tampering | retention run deleting live data | high | mitigate | Horizon from cleanup-logic parity constants; dry-run first (default true); ≤5000-row batches; maintenance lane only; D-37 audits writer consistency |
| T-04-28 | Information Disclosure | alert payloads/report logs carrying user data | low | mitigate | Templates carry exactly what today's alerts carry (parity is the contract); dry-run reports carry ids/counts only; no tokens in log lines |
</threat_model>
